# Supervisor 中枢：hub 自建 PM 设计

日期：2026-10-19
状态：待评审
前作：2026-10-15-ai-factory-orders-design.md（本文档取代其中「PM 提示词承载流转」的决定）

## 一、要解决的问题

前作把「谁来决定下一步做什么」交给 PM 提示词和节点自律，导致：

1. 角色只是 Map 里的字符串，没有任何代码读它
2. `by` 参数由调用方自报，任何节点都能冒充 PM
3. 派发不经过任何中枢，`mac_send_task` 可随意绕过工单
4. PM 靠 worker 拉活，退出即失忆，无法持续盯进度

结果是 PM 沦为提示词模板，已整体退役（提交 3f91cb5）。

系统原本的目标是多 agent 设计模式中的 Supervisor 模式：
一个中枢决定谁做什么，worker 之间可自由通信。

## 二、核心定义（本文档的第一原则）

### 2.1 调度控制流与通信数据流分离

   调度控制流  谁决定下一步做什么          → Supervisor 独占
   通信数据流  worker 之间说话、传文件      → 直接放行，Supervisor 只观察

worker 之间可以自由交谈，但「因为这轮交谈，所以我要开始做另一件事」必须由 Supervisor 决定。

### 2.2 派发权属于 hub，PM 只是被授权使用它

PM 不是被赋权的实体，而是 hub 派发权的临时持有者。由此推出：

- 没有 PM 时系统自然回到人工，不是故障
- 人随时可以接管，不必等 PM 超时
- PM 失联时权限自动收回，系统不会僵死

### 2.3 拦截与豁免

| 动作 | 通道 | 规则 |
|---|---|---|
| 节点间留言 | mac_send_message | 放行，全部进事件流供 PM 观察 |
| 新任务派发 | mac_send_task / 工单 dispatch | 仅 PM 或人类可发起 |
| 同工单内返工 | mac_send_task 且双方都是该单 assignee 历史参与者 | 豁免，放行 |
| 跨工单派活 | 任意 | 必须经 PM |

豁免的判定依据是「不改变谁为哪张单负责」。返工只是把同一张单再推一轮。

## 三、架构

    ┌──────────────────────────────────────────────┐
    │ hub 进程                                      │
    │                                              │
    │  ┌────────────┐   事件流   ┌──────────────┐  │
    │  │ 事件总线    │ ─────────→ │ 决策调度器    │  │
    │  │ (EventBus) │            │ (Dispatcher) │  │
    │  └────┬───────┘            └──────┬───────┘  │
    │       ↑                           │ 动作数组  │
    │  ┌────┴───────┬───────────┐       ↓          │
    │  │ OrderStore │ Registry  │  ┌────────────┐  │
    │  │            │           │  │ 授权门禁    │  │
    │  └────────────┘           │  │ (Gate)     │  │
    │                           │  └─────┬──────┘  │
    │                           └────────┼─────────┘
    │                                    ↓
    │                            enqueueFor（唯一派发出口）
    └──────────────────────────────────────────────┘

三个新增模块，均在 packages/server/src 内，保持零外部依赖：

| 模块 | 职责 | 规模预估 |
|---|---|---|
| events.ts | 事件总线：采集、去重、去抖合并 | ~120 行 |
| pm.ts | 决策调度器：配置、LLM 调用、动作解析、记忆 | ~350 行 |
| gate.ts | 授权门禁：派发权状态机、拦截判定 | ~120 行 |

## 四、事件模型

### 4.1 事件类型

    order/created       工单建立
    order/status        工单状态变更（含 by、from、to）
    order/assigned      assignee 变更
    task/completed      任务终态（completed / failed / canceled）
    task/input-required 节点等人工确认
    node/online         节点上线
    node/offline        节点下线
    mail/sent           节点间留言（只观察，不触发决策）
    pm/tick             兜底扫描（低频）

### 4.2 采集方式

现有 OrderStore / Registry 均无回调钩子（已核实）。采用最小侵入：

- OrderStore.create / update / attach / detach 末尾 emit
- Registry.heartbeat / sweep 的 online 翻转处 emit
- reportResult 内已调用 syncOrderFromTask，在其后 emit task 事件

不引入 EventEmitter 依赖，自己实现一个 ~40 行的轻量订阅表即可。

### 4.3 去抖合并

事件入队，去抖窗口（默认 3000ms）内的多个事件合并成一批，一次决策。

    拆 5 个子单 → 5 个 order/created → 合并为 1 批 → 1 次 LLM 调用

保底扫描：每 5 分钟一次 pm/tick，防事件漏收导致工单僵死。

### 4.4 防自激发

PM 自己产出的动作会导致新事件，若不处理会死循环。

规则：动作执行期间产生的事件标记 causedBy="pm"，不进入触发队列，
只写入决策日志。下一轮决策仍能在全局快照里看到它们。

## 五、决策输入（固定 token 预算）

每次决策构造一个输入，总预算默认 6000 token，超出按优先级裁剪：

    1. 策略文件           pm.policy.md       （全量）
    2. 铁律清单           代码内常量          （全量）
    3. 本批事件           去抖合并后的事件    （全量，最多 20 条，超出截断）
    4. 全局工单快照       未完成工单摘要      （按优先级 + 更新时间的 Top 30）
    5. 节点快照           名称/角色/能力/负载 （在线节点全量）
    6. 记忆摘要           最近决策 + 节点表现 （最近 10 条）

工单摘要字段：id / title / status / assignee / parent / blockedBy / 更新了多久

## 六、决策输出（结构化动作）

LLM 必须返回 JSON，格式：

    {
      "reasoning": "一句话说明判断依据",
      "actions": [
        { "kind": "create_orders", "orders": [{ "title": "...", "description": "...",
          "parent": "ord-xxx", "priority": "high", "blockedBy": [] }] },
        { "kind": "assign", "orderId": "ord-xxx", "assignee": "dsh-PC-hake", "note": "..." },
        { "kind": "update_status", "orderId": "ord-xxx", "status": "review", "note": "..." },
        { "kind": "send_message", "to": "dsh-PC-hake", "text": "..." },
        { "kind": "noop" }
      ]
    }

动作种类刻意保持少：五类覆盖全部编排行为。每种动作执行前都过门禁校验。

## 七、铁律门禁（代码强制，不靠提示词）

以下规则由 gate.ts 硬性校验，违反则驳回该动作并记日志：

1. PM 不能把任务派给自己
2. 目标节点必须在线
3. 依赖未完成的工单不能离开 backlog（force 仅人类可用）
4. 状态流转必须单调，不允许 done → developing
5. 一张单的 assignee 变更必须写 note
6. 单次决策的动作数上限（默认 10），超出整批驳回重判
7. 同一工单 10 分钟内不允许被 PM 修改超过 3 次（防抖环）

门禁驳回不导致整次决策失败，只丢弃该动作，其余照常执行。

## 八、派发权状态机

    ┌───────────┐  人开启（控制台）  ┌───────────┐
    │ human     │ ─────────────────→ │ pm        │
    │ 人工模式   │ ←───────────────── │ PM 模式    │
    └───────────┘   人手动切换        └───────────┘

| 状态 | 派发拦截 | 触发条件 |
|---|---|---|
| human | 不拦截，人工指派 | 默认状态；人手动切换 |
| pm | 拦截，仅 PM / 人 / 工单内返工放行 | 人在控制台开启 |
PM 失败只告警不放手：连续决策失败累计 failStreak，控制台标红提示，
派发权仍归 PM。放行永远由人决定，不存在超时自动降级。

## 九、记忆

落盘 .pm-memory.json，三层：

    decisions[]  最近 200 条决策：时间、触发事件、动作、执行结果、门禁驳回
    nodes{}      节点统计：派发次数、完成率、被打回次数、最近活跃
    orders{}     工单历史：打回次数、耗时

注入决策的只是压缩摘要（最近 10 条 + 节点的完成率与打回率）。
完整记忆供控制台查看，也是后续评估 PM 质量的依据。

## 十、配置

文件 .pm-config.json（与 .orders.json 同级）：

    {
      "enabled": false,
      "baseUrl": "http://127.0.0.1:11434/v1",
      "apiKey": "",
      "model": "qwen2.5:14b",
      "temperature": 0.2,
      "debounceMs": 3000,
      "tickMs": 300000,
      "maxActionsPerDecision": 10,
      "tokenBudget": 6000,
      "timeoutMs": 60000
    }

baseUrl 支持任意 OpenAI 兼容端点：ollama / vLLM / LM Studio / one-api / 官方 API。
apiKey 留空则不发送 Authorization 头（本地模型常见）。

配置读取优先级：.pm-config.json > 环境变量 > 默认值。
控制台提供表单编辑，保存后热生效（不需要重启 hub）。

apiKey 不明文回显给前端，控制台只显示「已配置 / 未配置」。

## 十一、控制台

新增 PM 面板：

- 总开关（开启 / 关闭 PM 接管），显示当前派发权状态
- 配置表单（baseUrl / model / apiKey / 各阈值）
- 决策流：实时显示最近 N 次决策（触发事件 → 推理 → 动作 → 结果 → 是否有驳回）
- 记忆查看：节点统计表、工单历史
- 手动接管按钮（任何时候可用）
- PM 连续失败时状态卡标红提醒（只提示，不改变派发权）

## 十二、失败处理

| 情况 | 处理 |
|---|---|
| LLM 超时 | 记日志，本批事件丢弃不重试，等下一批 |
| 返回非 JSON | 尝试提取第一个 JSON 块；仍失败则记「决策失败」，本批作废 |
| 返回非法动作 | 门禁逐条驳回，其余执行 |
| 连续决策失败 | failStreak 累加，控制台标红提示人介入；派发权不自动放开 |
| 动作执行抛错 | 该动作为失败，不影响其他动作 |

## 十三、不做（YAGNI）

- 不做 PM 主动读文件验收产物（后续增量，先靠工单 description 和附件 URI）
- 不做 PM 的多轮工具调用（纯单次决策）
- 不做跨 hub 编排
- 不做 PM 自动恢复（必须人确认）
- 不把 PM 做成独立进程（就在 hub 内）

## 十四、实施拆分

1. **events.ts + 采集点**：事件总线、去抖、OrderStore/Registry 埋点
2. **gate.ts**：派发权状态机 + 拦截逻辑 + enqueueFor 接线
3. **pm.ts 骨架**：配置读取、LLM 调用、动作解析，先接一个固定的 prompt 打日志不执行
4. **动作执行器**：五类动作对接现有 store，逐条门禁校验
5. **记忆**：.pm-memory.json 读写与压缩注入
6. **控制台**：PM 面板、决策流、手动接管
7. **文档**：install.md 增补 PM 章节，说明「无 PM 时人工模式如何运作」

第 1-2 步可以先把「强制拦截」跑通，此时即使没有 LLM，人工派发也完全可用。
这是最小可交付形态。
