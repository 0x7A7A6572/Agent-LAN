## 【关键机制】新版 worker 为什么不再唤醒会话（14:00 查清，已修复）
- **老版靠什么通知会话：后台子进程退出事件（task-notification）**，不是 hub 推送、不是消息注入。链条：会话 `run_in_background` 起 worker → 脚本 long-poll → 拿到任务就 `exit 0` → 宿主检测到进程结束 → 投递 `<task-notification>` → 会话拿到新 turn → TaskOutput 取任务 JSON → 干活 → `mac_report` → 再起 worker。**「退出」就是敲门砖。**
- **新版（≥479b36c0）剪断了这根线**：注释与 install.md 都写「常驻轮询不退出，领到任务只打印 JSON 继续轮询」。进程永不结束 ⇒ 永无 task-notification ⇒ 空闲会话永远不醒。JSON 只落在后台任务缓冲区，没人读。install.md「上层会话的处理循环」整节**没有写会话空闲时靠什么被叫醒**——指南的漏洞，值得单开一单。

## 唤醒通道的"协议"定性（14:08 核实）
- `bell.sh` **是我本地写的，不是官方分发**：hub `GET /bell.sh` → 404，`GET /worker.sh` → 200（官方只分发 worker.sh，源码在 `packages/server/src/worker.sh`），install.md 里 `bell` 零命中。好处是它不在 worker 自更新路径上不会被冲掉；坏处是 hub 将来官方修好唤醒后需要手动下线它。
- `<task-notification>` **不是网络协议**，是宿主（WorkBuddy agent runtime）在"自己管理的后台任务结束"时注入对话的内部控制消息，带 `task-id` / `tool-use-id` / `status`。worker 无法发送；外部唯一能影响的是"子进程何时退出"，所以 exit 才是可编程信号。
- **hub 没有实现 MCP 服务端主动通知**：`packages/server/src/index.ts` 全文 grep 无 `notifications/`、无 `sendNotification`。唯一真实时推送是 `/console/presence/stream`（给浏览器控制台的 SSE，卡片 1 秒变蓝就靠它）——与 agent 会话无关，这正是"控制台能看到、会话不知道"的根因。
- 结论：当前只有三条可编程唤醒通道 —— ① 子进程退出（在用，bell.sh）② 定时 automation（延迟最差一整个周期）③ MCP server-initiated notification（协议上存在，但 hub 未实现 + worker.sh 是 curl 轮询不是长连 MCP 客户端，路是断的）。

## 反驳「worker 自己就能推送通知」（14:12 核实）
- 别处流传的方案 A：`MAC_TASK_HOOK=<命令>`，worker 命中任务时执行钩子。
- 查证：现版 worker.sh 支持的 MAC_ 变量只有 `MAC_DIR` / `MAC_ROOT` / `MAC_SESSION_ID`，`hook` 关键词 **0 命中** → 方案 A 是提议，不是现状。
- 更要命的：**宿主没有向运行中会话注入消息的通道**。`codebuddy` CLI 子命令实测只有 `config/mcp/sandbox/plugin/project/doctor/update/install/cleanup/daemon/ps/logs/attach/kill/stop/rm/respawn/agents/auto-mode`，**无 send / inject / notify**。所以 bash 进程"直接触发通知"这句话在"通知=送达会话"的语义下不成立。
- 一个 bash 进程能做的只有三种：写文件（空闲会话没人读）、调 hub MCP 工具（只改 hub 状态，控制台走 SSE 能看到，会话不订阅）、**让宿主管理的子进程退出**（唯一能触达会话的路径）。
- 所以 MAC_TASK_HOOK 的真实价值在**触发层**（把"命中时做什么"做成可插拔），不在**传输层**。钩子若想真唤醒会话，内容最终仍须落到 `exit`，就退化成旧版语义且更差（命中即死、心跳中断）——正是新版要解决的问题。
- 分层结论：触发层（worker 轮询，已有）/ 传输层（宿主后台任务退出，唯一现成；MCP notification 需两端实现，当前无）/ 唤醒层（读 node.json → 干活 → report）。bell.sh 是"用触发层模拟传输层"的胶水。
- 判定谁对的可执行办法：让主张方落地 MAC_TASK_HOOK，钩子里只做 echo/curl，然后不看 TaskOutput —— 会话不会醒。

## 「MCP 无状态所以不能保持连接」是误解（14:18 核实仓库代码）
- **协议事实**：MCP Streamable HTTP 是三件套并存 —— ① 每个 POST 自带完整信息、可无状态处理（方便水平扩展）；② `Mcp-Session-Id` 做协议级会话关联；③ 客户端 MAY 对 MCP 端点发 `GET` 开一条 **standalone SSE 下行流**，专收 server-initiated messages（`notifications/*`）。所以"无状态"≠"不能长连"，这俩不互斥。必须长连的是**已被取代的老 HTTP+SSE 双端点**传输。
- **本仓库事实：管子挖了，没铺线**。
  - `index.ts` GET `/mcp` 分支：开 SSE、15s 发 `: ping`、注释写「服务端主动消息时可用」，但 `res` **没有登记进任何集合**，全文也没有任何一处往这条流写 JSON-RPC → 纯空壳占位。
  - `mcp-facade.ts:440` 只做了 `res.setHeader("mcp-session-id", randomUUID())`，服务端**没有 sessionId→订阅者 的索引表**，等于发了号没建档。
  - 对比真有发送侧的两条：`presenceSubs`（`/console/presence/stream`，控制台卡片实时）和 `sseClients`（`/tasks/:id/stream`，按任务推）。这俩是有 `Set` 登记 + 写入的，才是真的。
  - `packages/client`（`@mac/client`）存在但**零 SSE / 零订阅代码**，也是纯轮询。install.md 那句"行为一致"确实一致——一致地只会轮询。
- **最深一层**：即使铺好管子，`notifications/message` 送达 MCP 客户端 ≠ 唤醒会话。宿主是否把外部通知转成一个新 turn 是**宿主策略**，不是协议能力；CLI 无 send/notify 接口也印证这点。
- 所以 push 值得做，但收益是「降延迟 / 省掉 N 秒轮询 / 供控制台与第三方客户端订阅」，**不解决「叫醒会话」**。叫醒仍然只有进程退出这一条。
- 要做的话改动点：① GET `/mcp` 建 `Map<key,Set<ServerResponse>>`；② initialize 时把 sessionId 绑定到节点名；③ 新增 `pushMcpNotification()`；④ 在任务投递/留言写入处调用；⑤ 客户端换常驻订阅。
