# ord-2b436caf 交付：LAN 多节点协同跑通

节点 dsh-PC-hake · 2026-10-16

## 目标

> 让项目能跑通完整的 LAN 多节点协同工作模式（AI 工厂，每个节点一个角色，
> 如产品、测试、开发），目的是流程跑通。

## 结论：流程已跑通

## 一、跑不通的直接原因

接手时**只有 1 个节点在线**（dsh-PC-hake），而"多节点协同"至少要两个角色。
wb-dev-pc-win11（测试）的 worker 不在，节点离线——单节点无论怎么操作都演不出协同。

修：给两个节点各配独立监督进程，保证 worker 常驻、节点不掉线。

| 节点 | 角色 | 状态 |
|---|---|---|
| dsh-PC-hake | 开发 | 在线 |
| wb-dev-pc-win11 | 测试 | 在线 |

## 二、实测的完整协同链路

### 跨节点派活
开发节点建母单/子单 → 派任务给自己 → 完成上报 → 子单转派测试节点
→ 通知测试节点 → **任务成功投递（deliveredTo 正确、进入 working）**。

### 三角色流水线（依赖链顺序解锁）

建三张平级子单挂在同一母单下，用 blockedBy 表达先后：

    ① 产品阶段  (dsh-PC-hake)
    ② 开发阶段  blockedBy=[①]
    ③ 测试阶段  blockedBy=[②]

实测过程：

    ① 产品完成上报           → 工单 done
    ② 依赖①满足后推进        → developing → 完成 → done
    ③ 依赖②满足后进入测试     → testing → 转派测试节点 → 完成 → done
    母单收口                 → done

### 依赖门禁（AI 工厂的顺序保证）

①未完成时强行推进②：

    依赖未完成: ord-4127c88a（force=true 可强制）

**被正确拦截**，顺序保证有效。

## 三、过程中澄清的一处校验规则

建子单时若 parent 与 blockedBy 指向同一张单，会被拒绝：

    不能依赖自己的父工单

这是**正确设计**：parent 是归属关系，blockedBy 是依赖关系，二者语义不同。
正确建模是「三张平级兄弟子单，同挂一个母单，用 blockedBy 串先后」。

（另注：MCP 的错误在 error 字段而非 result，只看 result 会误得 undefined，
排查工具调用时需要判 error。）

## 四、遗留与边界

- 角色由人在控制台维护，当前允许列表为「需求分析+产品 / 开发 / 测试」；
  在线两节点角色齐备，可按 role 选人。
- 节点保活已自动化（独立监督 + 自愈实测），但任务执行仍需上层 agent 参与：
  worker.sh 拿到任务即退出，监督会立刻拉起新的，任务需要有人处理。
