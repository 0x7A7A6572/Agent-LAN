# ord-53288b36 分析：多会话架构变更

节点 dsh-PC-hake · 2026-10-19

## 一、现状验证（实测）

### 1.1 当前模型：节点 = 单消费者

身份只有一层——`name`（节点名）。服务端三张表全按 name 作 key：

    pullWaiters: Map<string, waiter[]>   // 谁的 pull 在挂起
    pullQueues:  Map<string, Task[]>     // 派给谁的任务堆积
    registry:    Map<string, AgentPresence>

`mac_check_in` 的字段只有 name / agent / description / host / abilities，
**没有任何会话标识**。

### 1.2 多会话同 name 的实际行为——互踢（实测证实）

现状设计是「会话接管」：同 name 只允许一个活跃 waiter，新 pull 抵达即踢掉旧的，
被踢者立即空手返回（注释原文：「保证任务单消费者，多会话共用身份时不会互抢」）。

实测（两个并发 mac_pull_task，同 name=dsh-PC-hake，waitMs=12000）：

| 请求 | 结果 | 耗时 |
|---|---|---|
| 并发 pull A | task: null | 立即返回（被踢） |
| 并发 pull B | task: null | 立即返回 |

对照组（单个 pull，waitMs=3000）：正常挂起 **3422ms** 到超时。

结论：并发时两者都**立即**返回 null，而非各自等到超时——互踢确实发生。
且**被踢的一方无法感知自己是被踢还是真没任务**，这是当前设计的盲点。

### 1.3 worker.sh 与"会话"的关系

worker.sh 每次 mcp_call 都会 initialize 拿一个新的 mcp-session-id，
但**只用于协议握手，从不作为身份**。所以协议层已有会话概念，业务层完全没用。

## 二、方案评估

### 2.1 判断：方向正确，但"每个会话一个 id"要落到正确的层级

用户方案：给每个会话注册单独 id，节点卡显示会话列表，任务绑定到会话而非节点。

**可行的部分**：把「执行单元」从节点细化到会话，确实能解决三个现有痛点——

1. 互踢导致的多会话不可用（现在的核心痛点）
2. 任务归属模糊：任务只知道"派给某节点"，不知道"哪个会话在跑"
3. 无法并行：同节点多会话无法各领各的任务

**必须修正的部分**：不要把 session id 当成新的任务路由 key。否则会出现
「任务派给节点，但该会话已死」的悬挂问题——这正是现在"投递丢失"问题的放大版。

### 2.2 建议模型：三层，而非两层

    主机 host  ──  节点 node(name)  ──  会话 session(sid)
    机器标识        程序+身份              一次接入的进程

- **node 仍是任务路由的稳定锚点**（工单、派活、名册都指向它）
- **session 是执行权的持有者**：任务由某个 session 领走并占用，node 只是容器
- 关键规则：**任务归属绑定到 session，但路由仍以 node 为目标**

类比：node 是「部门」，session 是「坐在工位的人」。任务派给部门，由某个在岗的人接手；
人走了任务退回部门队列，而不是凭空消失。

### 2.3 更优方案的关键点

比"每会话一个 id"更重要的三件事：

**① 会话要有独立的存活判定**
现在 name 的 lastSeen 是节点级。多会话后必须按 sid 维活，否则一个会话卡死会拖累整个节点。
建议 sid = 客户端自报的稳定串（如 host:pid:startup），服务端不生成，避免重连换 id。

**② 任务状态机要加"占用者"**
Task 目前有 deliveredTo(name)。需要加 claimedBy(sid) 与 claimedAt。
会话失联 → 只释放它占的任务，不影响同节点其他会话。

**③ 互踢必须改成排队或按需分配**
现在是"新踢旧"(粗暴)。有 sid 之后应改为：
同 node 的多个 session 各自独立挂起，任务按 FIFO 派给**任意一个空闲 session**；
不再需要互踢。这直接消除 1.2 的盲点。

### 2.4 缺陷与风险（必读）

| 风险 | 说明 | 缓解 |
|---|---|---|
| **兼容性断裂** | 所有 MCP 工具现在只认 name，加 sid 是协议变更；老客户端不带 sid 会怎样必须定义 | 不传 sid 时退化为「节点级匿名会话」，行为与现在一致 |
| **会话泄漏** | 崩溃会话不注销会在卡片上堆积 | sid 带心跳超时，超时即下线并退回其占用任务 |
| **身份膨胀** | 会话数 × 节点数可能导致卡片爆炸 | UI 只显示"活跃会话数 + 折叠列表" |
| **归因链变长** | mac_report 的 by 现在是节点名，加会话后要决定 by 是 name 还是 name/sid | 建议 timeline 记 name，任务级记 name+sid |
| **改动面大** | 三张表 + 20 处引用 + 前端卡片 + 全部工具签名 | 见第三节 |
| **收益是否够** | 若实际只有 1-2 个会话在跑，为它改造整个协议可能不划算 | 建议先确认：是否真有"同节点多会话并行"的真实需求 |

### 2.5 我的建议

**分两步走，不要一次大改**：

- **第一步（低成本、立竿见影）**：只做「会话可见」
  加 sid 到 check_in/pull（可选参数），节点卡显示活跃会话列表与各自状态；
  任务仍按 name 路由。这一步不动路由逻辑，风险极低，先解决"看不见"的问题。

- **第二步（视需求再做）**：真要做会话级执行权，再改任务路由与状态机。

如果第一步行得通、且确实出现多会话抢任务的真实痛点，再做第二步。

## 三、改动影响范围预检（按第一步估算）

### 3.1 后端（packages/server）

| 文件 | 改动点 | 量级 |
|---|---|---|
| mcp-facade.ts | mac_check_in / mac_pull_task / mac_report 增加可选 sid 参数；schema 更新 | 中 |
| registry.ts | AgentPresence 增加 sessions 表；会话级 lastSeen；sweep 时清理过期会话 | 中 |
| index.ts | checkIn/pullTask 传入 sid；presence 输出会话列表；会话失效时释放其占用 | 中大 |
| sdk/index.ts | AgentPresence 增加 sessions 类型定义 | 小 |

### 3.2 前端（web-console/src）

| 文件 | 改动点 |
|---|---|
| types/console.ts | Presence 增加 sessions 字段 |
| components/console/NodeCard.vue | 卡片显示活跃会话列表（折叠、显示状态/最后活跃） |
| stores/console.ts | 无（presence 流已全量推送） |

### 3.3 客户端脚本（worker.sh / probe.sh）

worker.sh 需要生成并持续上报一个稳定 sid。当前每次 mcp_call 都新拿 session，
要改成「进程启动时生成一次 sid，全程复用」。这是**必要的**，否则会话列表每次心跳都在变。

### 3.4 兼容性

- 老客户端（不带 sid）：退化为节点级，行为不变 → **向后兼容**
- 新客户端 + 旧服务端：sid 被忽略 → **优雅降级**

### 3.5 如果做第二步（会话级路由）

额外涉及：Task 加 claimedBy/claimedAt、pullTask 重写为会话维度、
回收逻辑按会话判定、console 任务列表显示会话归属、全部 order 工具的归因口径。
**当前 pullTask 有 20 处 name-keyed 引用需要逐一确认，属于中等重构。**

## 四、明确结论

1. **现状**：节点是单消费者，多会话同 name 会互踢，且被踢方无法感知（已实测）。
2. **方案方向正确**，但"任务绑定会话"要谨慎——应做成「路由按节点、占用按会话」的混合模型，
   否则会引入悬挂任务。
3. **建议分两步**：先做会话可见（低风险），再视真实需求做会话级路由（中高成本）。
4. **先决问题**：是否真有同节点多会话并行的需求？若没有，第一步足够；
   若有，第二步值得做，但需要接受协议变更与前端改造。

等你确认是否推进、以及推进到哪一步。
